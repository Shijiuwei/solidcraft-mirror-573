Edges made by booleans: each point evaluated once (2026-10-16)

A boolean meshes both operands with truck-meshalgo, which first divides every edge into a polyline (bounded_polyline, vendored). An edge that an earlier boolean made is an intersection curve. Each of its points is found by a grid search on each of the two surfaces, 51 × 51 evaluations of a NURBS surface each, before Newton. The division evaluated both ends of every piece again, so 2 of its 4 evaluations per piece repeated a point it already had. Profiles of main (01b1b705) on the machine below put the division at 42 % of the CPU time of opening the rover, 58 % of bench-agent and 82-85 % of a drilled hub or a union of tubes.

Each piece now carries the points of its ends, and its midpoint is both the probe and an end of both halves: 2 evaluations per piece. The fallbacks for samples that do not evaluate (#1364) are kept: a midpoint that fails is NaN as a probe and the curve's approximation as an end, exactly as before. The polyline is the same, bit for bit: edge_polyline_tests compares it with the previous division (points, order and number of evaluations) on the intersection curves of a drilled cylinder and on a circle.

STEP assemblies: a repeated part is meshed once (2026-10-14)

The reader already converts each B-rep item once and keeps it for the instances that list it again. Every instance still became a body of its own geometry (it has to: features cut and join it where it is), and each of those bodies made its own display mesh: tessellation, seam and tangent flags, the most expensive step of opening a large assembly. A board with 60 of each resistor meshed the same resistor 60 times.

A later instance of an item now shows its first instance's display mesh, placed by the difference of the two placements: the same triangles, faces and edge flags, moved. The mesh is made once, by whichever instance is drawn first. Only a rotation and translation is shared this way (anything else meshes itself), and anything that changes what a body shows (split lines; any operation, which makes a new body) drops the link. Measurements, booleans and export read the instance's own geometry as before, so solidcraft-cli eval of an assembly is unchanged.

Designs built by agents: work per command that grew with the design (2026-10-14)

A design an agent builds over MCP is made of many small commands: a cylinder per spoke, a box per chain plate, one part built at the origin and its component moved into place. Each command did work over the whole design, so the 1,000th command cost far more than the first and a 1,300-body design took minutes to build and to show. solidcraft-cli bench-agent builds such a design (a generated bicycle: about 1,260 commands, 1,280 bodies, 1,250 features, wheels built at the origin and moved), timing each command and then what a window needs to draw its result (the world state and its display meshes), and finally opens the saved design like bench-open. The script is generated, so it needs no fixture; --scale changes the counts and --script-out writes the commands for replaying elsewhere (engine.execute one by one over the control channel reproduces the desktop case).

What grew with the design, per command:

  • Moved components were placed again after every change. world_state transformed every body of a component whose occurrence is moved and gave it a new, empty display mesh, so every command meshed all those bodies again (the two wheels: 150 bodies and two tori, 130-190 ms per command). It now keeps the bodies it placed and reuses each one whose definition (same body, same display cell) and placement are unchanged.
  • A free dN name searched the design once per number (next_d_name), quadratic in the number of named inputs, for every new feature input.
  • Every expression evaluated every parameter (Document::eval), several times per feature command (each coordinate, each size). Parameters are now evaluated only when the expression names one.
  • The parameter table's used_by searched all parameters for each one (quadratic); it is one pass now. The desktop also stops gathering expression completions (eleven parameter tables) on every change while no text box has focus.

STEP import: shells and item solids without copies (2026-10-13)

A file that lists one product definition many times (a bolt used 70 times, a panel in several assemblies) is imported item by item, and every item's B-rep was deep copied twice before it was handed on: once by the caller of Solid::try_new, which clones the shells so that the failure path still has them, and once by the reader's own cache, which kept the solid for a later item that might list the same definition.

read_item now runs those four checks (non-empty, connected, closed, no singular vertices) on borrowed shells, so a shell that passes is moved into the solid instead of cloned. The reader keeps each prepared solid in an Arc, and an item counts as once when one representation lists it and exactly one product-definition walk reaches it: that item's solid is moved out of the cache with Arc::try_unwrap instead of copied, because no later item can ask for it. The walk follows MAPPED_ITEM targets too, so an item reached through a mapping in another product's node is still converted once - a second conversion would repeat that item's warnings. A file whose walk exceeds the work budget (MAX_CLOSURE_WORK, 65 536 nodes) falls back wholesale to the copying path, as does any file with component occurrences, which walks a definition again per instance.

Nothing observable changed. Fifteen fixtures (primitives, a void, a fillet, a revolve, colours, centimetre units, 70 duplicates of one definition, a broken file with mappings, a two-instance assembly and an expanded one; 99 bodies) give the same import dump - name, path, closed flag, file faces, face origin, topology and merged counts, bounding box, volume, area, centroid, paint, warnings and tree - apart from the per-feature milliseconds, and all fifteen STEP in/out round trips are byte-identical.

Display tessellation plans (#303, 2026-10-12)

Body::display_mesh meshes from a TessPlan (crates/kernel/src/tess): every edge is sampled once and both faces use those nodes exactly (watertight by construction); planar faces are a constrained Delaunay triangulation of their edge nodes alone; faces bounded by their parameter box are structured grids zipped to the edge nodes; other four-cornered faces are Coons grids; only genuinely trimmed curved faces (holes, more than four corners) use spade's constrained Delaunay with sag and Ruppert refinement. A body the planner cannot handle is meshed by truck-meshalgo as before, which also still meshes for modelling (booleans, measure, provenance). Evaluating a plan (surface points and normals) runs on the CPU (TessPlan::evaluate) or in a compute shader (solidcraft-gpu).

Parallel STEP body preparation (2026-10-12)

Profiling an original 48-cylinder STEP fixture before changing the importer measured 3.17 ms parsing, 6.06 ms reconstructing B-reps and 45.58 ms preparing/orienting bodies. The five complete imports had a median of 59.21 ms. The expensive orientation mesh, rather than the text parser, was the first parallelization target for #287.

Desktop import now prepares consecutive independent solids in a representation with up to eight workers. Each batch contains at most 64 solids. Parsing, B-rep reconstruction, assembly traversal, first-use unit resolution, naming and result collection remain ordered. Mapped items end a batch. Fewer than four solids use the serial path; wasm always uses it. Thread creation failure falls back to serial work, and kernel/worker failures remain per-body errors reported by the importer.

Windows x64, AMD Ryzen AI Max+ 395 (16 cores / 32 logical processors), optimized ci profile, no concurrent build: three fresh test processes per fixture, five alternating serial/parallel pairs in each process. These are complete uncached kernel imports, including parsing and body preparation; fixture generation/export and later desktop display meshing are outside the timer. Design storage: container and binary payloads (#303, phase one)

Design containers avoid formatting/parsing imported mesh coordinates as JSON numbers. The metadata serializer replaces embedded fields before creating JSON values, without cloning the full document or duplicating its schema. Binary coordinates retain f64 precision, indices retain u32, and SHA-256 deduplicates identical payloads. The reader checks archive budgets, CRCs, hashes, exact lengths, finite coordinates and index bounds.

Reproduce the storage measurements with an optimized ci IO test executable:

cargo test -p solidcraft-io --profile ci benchmark_ -- --ignored --nocapture --test-threads=1

The benchmarks generate an original 100,000-vertex/100,000-triangle mesh and a STEP containing 512 disjoint 10 mm boxes. Fixtures are written under CARGO_TARGET_DIR (or the crate's target directory). Each compares nine encoding/decoding samples; atomic-save samples include encoding, temporary-file flush, replacement and .bak creation and alternate JSON/container ordering. Documents are compared after decoding. These are storage measurements, separate from timeline evaluation or first-frame latency.

On Windows x64, based on upstream e6e0a7e before STEP parallelism (#312), three consecutive optimized runs without concurrent compilation gave the following medians of the three nine-sample medians (milliseconds, fast mode):

Three alternating fresh-process solidcraft-cli bench-open runs of each STEP encoding returned the same 512 bodies and 6,144 triangles. Median read-plus-parse was 2.274 ms for JSON and 2.151 ms for the container; median evaluation was 218.559/236.915 ms and display meshing 203.160/197.790 ms respectively. Geometry dominates and these variable results do not establish an end-to-end STEP opening improvement. Fresh processes do not imply a cold operating-system file cache, and these are not desktop first-frame times.

Fast mode stores STEP and mesh payloads directly. Explicit "compression":"compact" compresses them at Deflate level one; it is a space/CPU tradeoff. In the initial 512-box STEP experiment, compression reduced 1,998,793 JSON bytes to 578,659 package bytes but increased median encoding from 1.68 to 5.02 ms and decoding from 1.76 to 4.18 ms. That regression is why compression is not the default. PNG/JPEG are stored directly in either policy; small parametric metadata uses Deflate level one.

Plain JSON remains a supported Save As/export format; .json saves keep JSON and scripts may explicitly select either format. The CLI detects packages before attempting JSON parsing. Desktop/browser recovery and browser downloads also use the container. See the versioned container format for layout and bounds.

This phase does not restore evaluated B-reps, skip STEP import, or make cold geometry rebuilds instant. A matching cache key is not enough to trust unvalidated geometry. The native B-rep increment described below supplies provisional display, not editable session restoration. It is separate from #287's import parallelism.

Opt-in mesh preview measurements (#303, phase one)

The phase-one desktop implementation can show an experimental saved picture while the file worker rebuilds geometry. It requires an explicit preview: true engine Save/Save As call. Ordinary saves omit display meshes to avoid the measured overhead; these measurements predate native B-rep caching. The cache contains only already warm evaluated display meshes, capped at 8 MiB, 1,024 bodies and 100,000 triangles. Larger or cold models save without it. Cached geometry is never used for editing, measurements or picking. Source/document fingerprints and payload validation reject stale or malformed caches; cancellation and document/revision checks prevent a background result from replacing newer work.

The cached picture is prepared on the file worker from the same file snapshot as the normal Open command. It adds work before reconstruction, rather than bypassing it, so measure preview readiness and full editing readiness separately. Cached display also adds file size and save work; the storage-only results above exclude that optional data.

For an engine-level save benchmark, first generate the original 512-box STEP fixture with the ignored IO benchmark, then run the warmed-session benchmark:

cargo test --workspace --profile ci benchmark_step_storage -- --ignored --nocapture --test-threads=1
cargo test --workspace --profile ci benchmark_warm_design_save_with_preview -- --ignored --nocapture --test-threads=1

Set CARGO_TARGET_DIR to the workspace's absolute target directory in both commands. The engine benchmark alternates nine JSON/container atomic saves, includes the optional display cache, and verifies both preview decoding and authoritative document identity. Three runs on Windows, with no concurrent build or test suite, measured median atomic JSON saves of 7.679/7.610/7.630 ms and container-with-preview saves of 10.319/10.633/10.541 ms. Preview decoding took 0.964/0.961/1.130 ms; the container was 2,510,490 bytes. This optional preview costs save time on this STEP fixture. An actual desktop sensor-enclosure opening on e8a8e0f prepared its saved picture in 24.320 ms; geometry reconstruction, display warmup and thumbnail preparation took 8,913.212 ms. The same preview experiment is now explicitly opt-in; full geometry readiness still requires reconstruction. For actual desktop opening phases, launch with SOLIDCRAFT_PROFILE_OPEN=1: ready_ms reports saved-picture preparation, while the normal phase log reports reconstruction, display warmup and thumbnail completion. Neither log measures the exact GPU first frame.

Native cache opening (#303)

The portable native B-rep cache is opt-in with cache: true on warm container saves, without duplicating display meshes. Ordinary saves and browser downloads default to cache: false: the measurements below do not justify imposing the additional save time and file size on every design. Desktop Open reads metadata and optional geometry through a seekable file, produces a bounded provisional picture, then resolves original sources and reconstructs the complete session before editing. This improves the opportunity for early display, not the cost of authoritative feature evaluation. An absent, invalid or incompatible cache uses the original reconstruction. Browser OPFS/downloads share the format; browser opening still rebuilds synchronously.

The reproducible engine benchmarks separate atomic saving, provisional mesh readiness, reconstruction and final display-mesh readiness:

cargo test -p solidcraft-io --profile ci benchmark_step_storage -- --ignored --nocapture --test-threads=1
cargo test -p solidcraft-engine --profile ci benchmark_native_cache_save -- --ignored --nocapture --test-threads=1
cargo test -p solidcraft-engine --profile ci benchmark_native_cache_open -- --ignored --nocapture --test-threads=1

Use an absolute CARGO_TARGET_DIR. The save benchmark defaults to the generated 512-box STEP document and accepts SOLIDCRAFT_BENCH_FILE for another public design. It alternates nine saves of each encoding, including flush/replacement/backup, and verifies document identity and native-cache presence. It never times initial fixture evaluation as save work. Open runs once per process; SOLIDCRAFT_BENCH_ENCODING selects 0=JSON, 1=container without cache, 2=native cache, 3=compact native cache. Changing only cache/key.json's application version provides a cache-miss control. Fresh processes do not imply a cold operating-system file cache. The engine callback time is provisional mesh readiness, not a rendered desktop frame; use the desktop profile log and actual screenshots to check the saved picture and completed model.

Analytic extrusion source preparation

New-body extrusion certificates now prepare the sketch's bounded analytic segments once per certification pass instead of allocating segments and resolving their points for each generated cap boundary and side face. Saved designs run this same code during cold rebuilds. Exact containment tolerances, ambiguous-source rejection and the certification work budget are unchanged. Prepared segments borrow an immutable evaluated sketch and are not retained across edits.

The reproducible microbenchmark is:

cargo test -p solidcraft-doc --profile ci benchmark_prepared_extrude_sources -- --ignored --nocapture

Three Windows x64 optimized ci runs, during other compilation, compared the previous segment reconstruction loop and the prepared matcher in the same process. For 1,000 analytic lines and 1,000 generated face segments, median time fell from 45.90 ms to 12.30 ms (73% less, about 3.7x faster). Preparation is included and every returned source identity is compared. This measures certification only, not complete extrusion, file-open latency or Boolean operations; it does not establish an end-to-end loading speedup. Remaining cold geometry rebuild and import costs are tracked in #255; certification work is #254.

Prepared assembly geometry and selection

Prepared world geometry is now keyed by the document, evaluated model and exact placement context instead of the session revision. Selecting a face or edge, changing visibility, or moving the view no longer discards already prepared assembly bodies and meshes. Geometry edits, pending occurrence moves, authoring context changes, undo/redo and timeline rollback still invalidate the cache. Scratch sessions share prepared geometry while their inputs match, and adopting a computed session retains its warm cache.

On the private 2,990-body Pi assembly, a matched Linux desktop control probe reduced an edge-selection round trip from 9.24 s to 0.57 s. Initial opening stayed essentially unchanged (33.54 s to 33.32 s); this fixes a separate selection stall, not cold geometry evaluation. Three fresh Windows desktop runs with the corrected cache measured a median 15.87 s to ready: 13.04 s geometry, 2.20 s placement, 0.53 s meshing and 0.07 s thumbnails. These used the optimized ci profile and actual Vulkan rendering, with isolated settings and caches. Linux and Windows timings are separate measurements and must not be compared as a speedup.

Prism pairs, body measurements and the evaluation cache budget (2026-10-13)

A design whose features repeat one shape (a hole pattern, a plate cut by many tools, a part built by one growing body) pays several per-feature costs that a rebuild was paying again and again.

A body's size is measured once, not once per call. Every kernel tolerance is a fraction of the body's bounding-box diagonal, and Body::size() walked every vertex of the solid to work it out. Body::new already reads those vertices to orient the body, so it keeps the diagonal it measured there; a body built by hand, or a mesh body, still measures once.

The same volume is not measured twice. A boolean measures both operands' volumes to bound its result, and the body it returns becomes the next feature's operand, so a timeline of n cuts meshed every intermediate body twice. Body::volume_at(tol) keeps the last measurement for the solid, shared by its clones (they share the solid), and the bounds ask at the same tolerance every time.

A prism pair is decided in 2D before either operand is meshed. The general boolean builds a refined mesh of both operands before it can decide anything, and that mesh is most of its cost: a pattern, or a sketch with several profiles, rebuilds the whole target's mesh once per tool. A plate and a tool through it are prisms along one direction, which prism::prism_boolean decides exactly from their 2D sections - and that route ran after the meshes. A cut or an intersection now asks it first and returns without building them. A pair the route cannot answer takes the old path unchanged, meshes and all; a union still asks after the sampled shortcut. One answer is sent back to that shortcut on purpose: when the 2D route returns one of its operands (a tool that misses its target, or covers it whole), the sampled path returns that very body, so an untouched body keeps its identity in the timeline (ops::prism_fast_path_tests).

A placement reads its orientation from its matrix. Placing a body (a pattern instance, an aligned copy) used to mesh the whole copy to decide which way its faces point and to count the faces its coarse mesh misses. A rigid placement leaves both as they were; a mirrored one (a negative determinant) turns the solid inside out. Both are now read from the matrix, so only the geometry is transformed.

The evaluation cache is bounded by the bytes it keeps. It held the last 4096 results, and a result is as big as the model it holds, so a long editing session kept every superseded state: nothing dropped the entries nothing referred to any more. It now also holds at most 64 MiB, oldest first, and always keeps the newest result, so a single evaluation is never thrown away in the same breath.

Desktop loading and recent thumbnails (2026-10-10)

The Arduino Uno enclosure (19 features, 34 KB) and Raspberry Pi 5 case (24 features, 61 KB) each decode in about 1 ms. A release build spends roughly 12.1 s and 8.2 s, respectively, evaluating their geometry on this Windows machine. Changing the document encoding does not eliminate these boolean operations.

Interactive Open, recent-file clicks, drag/drop and STEP/mesh insertion now execute on a worker, including preparation of the world-space bodies and display meshes. The existing design stays available until the result is ready; a failed or cancelled job cannot replace it. Insertion preserves the file, saved state, earlier undo history and view settings. Timeline copies share their lazy mesh cell, and adopting a prepared session keeps its warm world-space cache instead of transforming and tessellating its components again on the UI. A STEP body's missing-face check reuses its orientation tessellation when the tolerances match and its orientation was not reversed.

Live desktop tests (ci profile, with other builds/tests running) opened the Arduino and Pi case in 15.2 s and 10.5 s. During those jobs, median ui.inspect round trips were 20.5 ms and 8.3 ms; the slowest were 33.7 ms and 28.6 ms. This fixes the window freeze, not the remaining cost of cold geometry evaluation.

Recent thumbnails are 240 × 150 PNG files in SolidCraft/thumbnails under the platform cache directory (LOCALAPPDATA on Windows). Their keys include the source path, file size and modification time. Open and Save render from the model already in memory. Cached recents decode the PNG without reading or rebuilding a document, and run before cold recents and sample thumbnails. Missing or invalid pictures fall back to a background rebuild. No thumbnail or base64 image is added to the design JSON. A regression test verifies the source bytes remain unchanged, a cached picture works even without a parseable source file, and changing the source invalidates the cache.

solidcraft-cli bench-open also accepts STEP/IGES. For exchange files its parse phase includes constructing and checking the imported B-rep, not merely decoding STEP syntax.

The live test loaded both cached recent cards in 21 ms and inserted the 2 MB lightweight Pi STEP (27 bodies) into the case in 279 ms; undo restored the original two bodies. The full 77 MB board STEP (2689 solid definitions, 45,689 faces) still had not completed after 300 s. Its window continued handling inspection and Cancel, and cancelling preserved the case. Complex STEP construction remains an outstanding kernel performance problem.

Sketch solver and drags (2026-10-11)

Unknowns the constraints pin down one after another from the constants (each one's own rows of full, well-conditioned rank, reading nothing but constants and unknowns pinned before it) are eliminated exactly: values the constructive seed placed and whose constraints hold there stay constants while Levenberg–Marquardt solves the rest, and the rank analysis (degrees of freedom, determined geometry) runs on the remainder only. A component tied to no constant takes one point as a constant first (its translation). All the held solves of one live drag frame share a 1M decomposition work budget (about 16 ms; a solve's own, 20M, is about 0.3 s), and a drag's steps are a quarter of the smallest held size instead of an eighth, except once a seed ran out of budget: the rest of that drag goes in eighths, as before, and continuation keeps the branch the seed no longer places.
